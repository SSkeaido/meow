# 引用准确性检查器产品方案

调研时间：2026-07-20

目标产品：一个面向论文写作者的 citation-grounded 引用准确性检查器，用来降低“引用漂移”和学术不端风险。

## 一句话定位

帮助用户在长期论文写作、修改、翻译和润色过程中，持续确认每个被引用的观点是否仍然被原始文献支持。

它不是单纯的“AI 写综述”，而是一个“观点-证据-引用”管理和审计工具。

## 用户痛点

论文写作周期长，被引用的句子会经历多轮改写：

```text
读文献 -> 写中文笔记 -> 写段落 -> 翻译英文 -> 语言润色 -> 导师/合作者修改 -> 投稿前压缩或重组
```

在这个过程中容易出现几个风险：

1. 原文只是说 A 相关，最后写成 A 导致 B。
2. 原文研究对象是特定人群，最后写成普遍结论。
3. 原文只是方法探索，最后写成已验证结论。
4. 多篇文献结论被混在一起，引用却只挂了一篇。
5. 语言润色后语气变强，导致证据支撑不足。
6. 修改太久后，作者忘记某句话到底来自哪篇文章。

## 核心原则

1. 每个被审计观点必须绑定至少一个可追溯证据。
2. 每个引用只能使用当前段落允许引用的文献。
3. 润色后的句子必须重新做证据匹配。
4. 系统可以辅助判断，但不能凭空创造引用。
5. 用户最终看到的不是“AI 很会写”，而是“这句话为什么能这么写”。

## 核心流程

```text
导入论文 PDF
-> 解析原文和页码
-> 生成 evidence cards
-> 导入待检查段落
-> claim extraction
-> evidence retrieval
-> citation audit
-> 导出报告
```

## MVP 范围

第一版建议只做一个小而完整的闭环：

1. 上传多篇 PDF。
2. 解析正文并保留页码。
3. 生成 evidence cards。
4. 导入待检查段落。
5. 对段落做 citation audit。
6. 导出 Markdown + 引用台账 CSV。

不建议第一版做：

1. 完整论文写作。
2. 自动综述生成。
3. 期刊投稿辅助。
4. 自动大规模爬文献。
5. 复杂图谱可视化。

## 技术路线

### 前端

第一版建议用网页，不建议先做小程序。

原因：

1. PDF 上传、审计报告、引用表格更适合桌面网页。
2. 小程序对复杂审计工作台不够舒服。
3. 后续可以把轻量阅读和进度查看迁移到小程序。

### 后端

推荐：

```text
FastAPI
PostgreSQL
pgvector 或 Qdrant
Redis
Celery / RQ
```

### 文献解析

可选：

```text
PyMuPDF
pdfplumber
GROBID
Marker
```

### 模型能力

需要三类模型调用：

```text
文献结构化抽取
引用审计与风险标注
润色前后语义漂移判断
```

## 与 LitReview+ 的关系

LitReview+ 的 README 中提到几个值得学习的思想：

1. evidence card，而不是直接把全文塞给模型。
2. context packet，而不是无限上下文。
3. citation allow-list，限制模型能引用哪些论文。
4. traceability chain，让每个观点能追溯到原文。
5. citation audit，生成后检查引用是否可靠。

但该仓库当前未发现明确 LICENSE 文件，因此不能直接复制代码或改造商用。我们可以学习思想和公开描述，重新实现自己的系统。

## 关键差异化卖点

```text
不是帮你更快地写完综述，
而是帮你检查这篇文章里的每句话为什么可以这么写。
```
