# Citation Accuracy Checker PRD

版本：v0.2

日期：2026-07-20

## 1. 产品定位

本产品是一个面向论文写作者的引用准确性检查工具。它帮助用户在长期写作、翻译、润色和修改过程中，持续确认每个被引用的观点是否仍然被原始文献支持。

核心卖点：

```text
不是帮用户自动生成综述，
而是帮用户检查已经写出的句子是否真的被引用文献支撑。
```

当前范围说明：

1. 这个程序只做引用准确性检查。
2. 前端不做综述段落编辑器。
3. 自动生成综述正文会放到另一个独立程序中。

## 2. 目标用户

1. 研究生、博士生、青年教师。
2. 需要写 literature review、related work、systematic review 的科研人员。
3. 害怕引用错位、过度概括、润色后语义漂移的论文作者。
4. 需要管理大量 PDF、引用和证据链的长期写作者。

## 3. 核心痛点

论文写作周期长，被引用的句子会经历多轮变化：

```text
读文献 -> 写笔记 -> 写段落 -> 翻译 -> 润色 -> 导师修改 -> 投稿前重组
```

风险包括：

1. 原文只是相关性，最后写成因果关系。
2. 原文研究对象有限，最后写成普遍结论。
3. 原文只是初步探索，最后写成成熟结论。
4. 多篇论文观点混在一起，但引用只挂了一篇。
5. 语言润色后语气变强，引用证据不再足够支撑。
6. 写作时间太久，作者忘记某句话到底来自哪篇文章。

## 4. MVP 目标

第一版只做一个可闭环的小产品：

```text
上传论文 PDF
-> 解析正文、页码和章节
-> 生成 evidence cards
-> 导入待检查段落或 claim
-> 执行 citation audit
-> 导出审计报告和引用台账
```

第一版不做：

1. 自动生成综述正文。
2. 前端段落编辑器。
3. 期刊投稿辅助。
4. 自动大规模爬取论文全文。
5. 复杂论文图谱可视化。
6. 替用户做最终学术判断。

## 5. 核心功能

### 5.1 文献导入

支持：

1. 上传 PDF。
2. 输入 DOI。
3. 导入 BibTeX。
4. 后续接入 OpenAlex、Crossref、Semantic Scholar、PubMed、arXiv。

### 5.2 PDF 解析

系统应从 PDF 中抽取：

1. 标题、作者、年份、期刊/会议。
2. 摘要。
3. 章节结构。
4. 正文段落。
5. 页码。
6. 参考文献。
7. 图表说明。

页码和原文片段必须保留，因为后续审计需要回溯到原文。

### 5.3 Evidence Cards

系统将论文转换为结构化证据卡片：

```text
研究问题
研究对象
方法
数据/样本
主要发现
局限
未来方向
可引用原文
```

每张 evidence card 必须包含：

```text
paper_id
claim_type
summary
source_quote
section
page
confidence
```

### 5.4 待检查文本导入

用户可以提交需要检查的文本，来源包括：

1. 手动粘贴段落。
2. 从外部草稿导入单段文本。
3. 导入润色前后两个版本做对比审计。
4. 后续支持从 Word / Markdown 中选中段落送检。

当前程序不负责编辑或生成这些文本，只负责检查它们的引用准确性。

### 5.5 Citation Audit

系统对每个段落执行审计：

1. 识别段落中的 claim。
2. 检查每个 claim 引用了哪些论文。
3. 检查引用论文是否在 allow-list 中。
4. 检查 evidence 是否支持该 claim。
5. 检查是否存在过度概括、因果夸大、对象泛化、引用错位。

审计结果：

```text
PASS: 支持充分
CHECK: 部分支持，需要人工确认
RISK: 存在引用漂移或过度概括
FAIL: 未找到支撑证据
```

### 5.6 润色后再审计

用户可以把润色后的段落重新导入，系统比较润色前后：

1. 语义是否变强。
2. 限定条件是否丢失。
3. 引用是否仍然适配。
4. 是否需要补充引用。
5. 是否出现新的 unsupported claim。

这是产品的关键差异化能力。

### 5.7 导出

第一版导出：

1. 审计报告 Markdown。
2. evidence cards CSV。
3. citation ledger CSV。
4. claim 审计结果 CSV。

## 6. PDF 解析与 Token 成本优化

PDF 解析不应主要依赖大模型。大模型只处理需要理解、判断和综合的小片段。

推荐管线：

```text
PDF
-> PyMuPDF / pdfplumber / GROBID 解析
-> 章节识别和段落切块
-> embedding 入库
-> 规则筛选核心章节
-> 小模型生成 paper cards / evidence cards
-> 检索相关证据
-> 大模型做 citation audit
```

### 6.1 非 LLM 解析优先

优先使用确定性工具：

```text
PyMuPDF
pdfplumber
GROBID
Marker
Science Parse
```

这些工具负责正文抽取、页码定位、段落切分、参考文献识别和图表说明提取，尽量不消耗 LLM token。

### 6.2 不把整篇论文直接喂给模型

禁止默认执行：

```text
把全文 PDF 文本直接发送给大模型总结
```

应改为：

```text
全文解析 -> 段落切块 -> embedding -> 检索 top-k chunk -> 只让模型处理候选片段
```

### 6.3 分层缓存

系统需要缓存：

1. PDF hash。
2. parsed chunks。
3. embeddings。
4. paper cards。
5. evidence cards。
6. audit results。
7. citation ledger。

同一篇论文再次使用时，不应重复解析和重复调用模型。

### 6.4 优先处理核心章节

第一轮 evidence extraction 优先处理：

```text
Abstract
Introduction
Methods
Results
Discussion
Conclusion
Limitations
```

在 token 预算有限时，先抽取这些章节，而不是全篇均匀处理。

### 6.5 小模型做粗加工，大模型做判断

可用便宜模型或本地模型处理：

1. 章节分类。
2. 关键词抽取。
3. chunk 摘要。
4. 候选证据筛选。
5. 初步 evidence card 生成。

大模型只用于：

1. 引用是否支撑 claim 的判断。
2. 润色前后语义漂移判断。
3. 复杂综合解释。

### 6.6 Claim 级审计

审计不重新读取全文，而是：

```text
claim -> embedding 检索候选 evidence -> LLM 判断 support / partial / unsupported
```

这能显著降低 token 成本，并让审计结果更可解释。

## 7. 隐私与数据安全

用户上传论文、草稿和审计记录都可能包含未发表研究、课题方向、投稿计划和个人学术资产。隐私设计必须作为核心产品能力，而不是附加说明。

### 7.1 用户的主要担忧

1. 上传的 PDF 是否会被平台保存。
2. 未发表论文草稿是否会被第三方模型使用。
3. 研究主题、选题方向和文献库是否会泄露。
4. 上传内容是否会被用于训练模型。
5. 删除文件后是否真的删除。
6. 团队协作时，谁能看到哪些材料。

### 7.2 产品承诺

面向用户需要明确表达：

```text
默认不使用用户上传内容训练模型。
默认不公开用户文献库、草稿和审计记录。
用户可以删除项目及其关联文件。
提供本地处理或私有化部署选项。
清楚标注哪些步骤会调用第三方模型。
```

### 7.3 数据处理模式

产品应提供三种安全等级：

| 模式 | 说明 | 适用用户 |
|---|---|---|
| 云端标准模式 | 文件上传到平台，调用云端模型处理 | 普通学生和轻量用户 |
| 隐私增强模式 | 文件加密存储，第三方模型只接收必要片段 | 重视课题隐私的科研用户 |
| 本地/私有化模式 | PDF、向量库和模型尽量部署在用户本地或机构内网 | 课题组、实验室、企业研发 |

### 7.4 最小化发送原则

调用第三方模型时，不发送整篇 PDF。只发送当前任务所需的最小片段：

```text
当前 claim
候选 evidence quote
必要上下文
引用元数据
```

避免发送：

1. 完整 PDF。
2. 用户整个文献库。
3. 全文草稿。
4. 与当前任务无关的论文内容。

### 7.5 隐私方案的具体执行方式

#### 云端标准模式

```text
用户上传 PDF
-> 平台云端对象存储保存原文件
-> 后端解析 PDF
-> 云端向量库保存 chunks 和 embeddings
-> 调用第三方模型生成 evidence cards 和 audit 结果
-> 用户在网页端查看和导出结果
```

#### 隐私增强模式

```text
用户上传 PDF
-> 平台云端加密存储
-> 后端本地解析、切块、向量化
-> claim 级检索候选 evidence
-> 只把 claim + top-k evidence quotes + 必要元数据发送给模型
```

#### 用户自带 API Key 模式

```text
用户填写自己的模型 API Key
-> 平台负责 PDF 解析、证据组织、流程编排
-> 模型请求使用用户自己的 API Key 发起
```

#### 本地/私有化模式

```text
用户本地或机构服务器部署应用
-> PDF 保存在本地或机构内网
-> PostgreSQL / Qdrant / MinIO 等服务本地部署
-> 模型接本地 Ollama / vLLM / LM Studio / 机构模型网关
```

### 7.6 第三方模型透明度

系统需要展示：

1. 当前使用的模型服务商。
2. 哪些内容会发送给模型。
3. 是否支持关闭云端模型。
4. 是否支持自填 API Key。
5. 是否支持本地模型。

## 9. 基于 LangChain 的低 Token 实现方案

本产品的 PDF 处理流程使用 LangChain 作为编排框架，但不把 LangChain 当成“把全文塞给 LLM”的工具。LangChain 主要负责文档加载、切块、向量检索、结构化输出、chain 编排和可观测性。

总体管线：

```text
PDF 上传
-> LangChain Document Loader 解析
-> 文本清洗和版面修复
-> RecursiveCharacterTextSplitter / 自定义 SectionSplitter 切块
-> Embeddings 生成向量
-> Vector Store 保存 chunks
-> Retriever 找候选证据
-> Evidence Extraction Chain 生成证据卡片
-> Citation Audit Chain 审计 claim 和 evidence 的匹配关系
```

LangChain 组件映射：

| 产品步骤 | LangChain 组件 |
|---|---|
| PDF 读取 | document_loaders |
| 文本切块 | text_splitters |
| 向量化 | embeddings |
| 向量库 | vectorstores |
| 证据检索 | retrievers |
| 多策略召回 | EnsembleRetriever / custom retriever |
| 结构化输出 | PydanticOutputParser / with_structured_output |
| 证据卡生成 | Runnable chain |
| 引用审计 | Runnable chain + retriever |
| 流程编排 | LCEL / LangGraph |
| 监控调试 | LangSmith，可选 |

第一版建议：

1. 用 LangChain LCEL 实现线性流程。
2. 不接 Review Generation Chain。
3. 审计失败后先输出修订建议，不自动改写。
4. 后续如果有长任务断点续跑、多步复核，再引入 LangGraph。

## 11. 当前模型职责与产品边界

本项目采用“确定性处理优先、模型负责理解和判断”的路线。模型不是用来替代 PDF 基础解析，也不是默认把整篇论文发送给云端模型。

### 11.1 当前处理链路

```text
PDF -> PyMuPDF 文本抽取
    -> 低文本页面按需使用 PaddleOCR-VL
    -> 分段、清洗、切块
    -> BGE-M3 向量检索
    -> BGE Reranker 重排候选证据
    -> Qwen 提取可核查主张
    -> Qwen 判断引用是否支持主张
    -> DeepSeek 复核高风险结果
```

### 11.2 模型的具体职责

| 环节 | 模型或工具 | 产品职责 |
|---|---|---|
| 普通 PDF 解析 | PyMuPDF | 提取正文、页码和段落，优先本地完成 |
| 扫描件识别 | PaddleOCR-VL | 只处理文本抽取不足的页面 |
| 文献向量化 | BAAI/bge-m3 | 将文献片段转换为可检索向量 |
| 候选排序 | BAAI/bge-reranker-v2-m3 | 从候选片段中排序最相关证据 |
| 主张提取 | Qwen | 将段落拆成可审查的事实性主张 |
| 引用判断 | Qwen | 判断支持、部分支持、不支持和风险原因 |
| 高风险复核 | DeepSeek | 对高风险结果进行独立复核 |

系统必须在审计结果中记录实际调用的模型、模型供应商和处理模式。模型输出只能作为审查建议，不得自动改写用户论文或声称“证明了学术事实”。

## 12. 受限文献审查 Agent 规划

### 12.1 产品定位

Agent 是后续的“深度复核助手”，不是替换现有固定审查链路的聊天机器人。普通检查继续使用固定流程；用户对疑难或高风险结果主动点击“深度复核”后，才启动 Agent。

### 12.2 Agent 可使用的工具

Agent 可以调用以下受控工具：

1. 在当前用户的文献库中检索片段。
2. 读取指定文献的前后页或指定页码。
3. 对低文本页面请求 OCR。
4. 对当前主张扩大或改变检索条件。
5. 比较多篇已上传文献的结论。
6. 调用主审模型和复核模型。
7. 生成带证据页码的深度复核结论。

### 12.3 Agent 的执行边界

每次 Agent 任务必须具备预算和停止条件：

- 最多执行 6～8 个步骤。
- 最多调用模型 3 次。
- 最多读取限定数量的文献片段。
- 超过预算时返回已有证据，不继续循环。
- 每一步工具调用写入审计日志。
- Agent 不得访问其他用户的项目、文献或历史记录。
- Agent 不得自动修改论文正文，只能提供修改建议。

### 12.4 首期 Agent 场景

首期只实现“深度复核”按钮，解决以下问题：

- 引用文献只支持主张的一部分。
- 论文措辞强于原文证据。
- 引用页码或文献绑定可能错误。
- 当前文献库证据不足，需要提示补充文献。

## 13. 一周访问密钥与用户工作区

### 13.1 密钥规则

系统使用邀请码作为访问密钥。新密钥默认从首次成功使用时开始计算，有效 7 天；有效期内默认不限审计次数。管理员可以按需要设置自定义有效天数或审计上限。

密钥必须满足：

- 后端只保存密钥哈希，不保存明文。
- 密钥通过 `X-Access-Key` 传递。
- 密钥首次使用后记录 `first_used_at` 和 `expires_at`。
- 过期密钥不能读取历史、上传文献或执行审计。
- 每个项目、文献、论文内容和审计记录绑定到密钥对应的工作区。
- 不同密钥之间必须进行数据隔离。

### 13.2 工作方式

用户可以在一周内分多次上传文献，再返回提交论文检查，不必一次上传全部资料。前端应显示密钥到期时间和当前工作区状态。

## 14. 批量上传与资源保护

### 14.1 用户体验

用户可以一次选择多篇 PDF，但前端按批次和队列提交。首期每批建议不超过 20 篇；超过部分提示用户在密钥有效期内分批上传。

### 14.2 后端处理原则

上传、解析和审计应分离：

```text
用户选择多篇 PDF
-> 文件保存和去重
-> 创建待处理任务并立即返回
-> 后台队列按受控并发解析
-> 解析完成后写入 chunks / embeddings
-> 前端轮询或订阅任务进度
```

2 核 2G 服务器的默认并发建议：普通文本 PDF 同时解析 1～2 篇，OCR 任务同时 1 篇，模型请求同时 2～3 个。系统不得因为用户一次选择 100 篇 PDF 而启动 100 个解析进程。

### 14.3 必须具备的保护机制

- 单文件大小和单批文件数量限制。
- 文件哈希去重，避免重复解析和重复计费。
- 任务状态：等待、上传中、排队中、解析中、向量化中、完成、失败。
- 失败任务可重试，重试次数有限。
- 处理超时、临时文件清理和磁盘空间检查。
- 服务器重启后可以继续未完成任务。

## 15. 用户历史与内容查看

### 15.1 历史入口

前端提供“我的历史”页面，只展示当前访问密钥工作区的数据，包括：

- 历史上传的参考文献。
- 文献标题、文件名、页数、上传时间和解析状态。
- PDF 解析出的正文内容和文本片段。
- 历史提交过的论文内容。
- 每次检查的时间、结果数量、风险等级和修改建议。

### 15.2 历史详情

用户点击某篇参考文献后，可以查看系统解析出的正文；点击某次论文检查后，可以查看当时提交的论文内容、引用证据和审计结果。历史详情必须经过当前访问密钥授权，不能通过猜测项目 ID 或批次 ID 访问。

### 15.3 数据生命周期

历史记录默认跟随访问密钥工作区保存。后续应提供用户主动删除项目、文献原文件、解析文本、向量和审计记录的能力，并在隐私说明中明确删除范围。

## 16. 分阶段交付优先级

1. P0：七天访问密钥、工作区隔离、历史文献和论文查看。
2. P0：批量上传限流、任务状态、去重和失败重试。
3. P1：当前固定模型链路的模型透明度和费用记录。
4. P1：针对高风险结果的 Agent 深度复核按钮。
5. P2：Agent 的公开文献检索、跨文献比较和自动化报告编排。

Agent 和云端模型必须采用可关闭、可限额和可追溯设计；在没有明确证据时，系统应输出“证据不足”，而不是让 Agent 自行补全学术结论。
