# 业主装修报价与承诺风险审查助手 PRD

## 1. 产品概述

### 1.1 产品名称

业主装修报价与承诺风险审查助手

### 1.2 产品定位

面向 C 端业主的装修签约前风险审查工具。用户在签约前输入装修报价单、合同条款和销售沟通记录，系统通过结构化知识卡、关键词/规则评分、本地相似度检索与 LLM 风险审查 Agent，识别报价不清、疑似漏项、增项风险、口头承诺未落纸、责任边界不明确等问题，并生成可追问、可留证、可复核的风险审查报告。

本产品不替代律师、监理或司法判断。产品输出应在报告中持续展示该边界说明：本报告用于签约前风险提示，不构成法律意见；涉及合同修改、赔偿、解约、责任认定等事项，建议人工复核。

### 1.3 一句话介绍

把装修签约材料转成一份有依据、有风险提示、有追问清单的签约前风险审查报告。

## 2. 背景与问题

### 2.1 行业背景

装修属于低频、高金额、高信息差消费。业主在签约前通常面对报价单、套餐说明、合同附件、销售承诺等大量非标准信息，但缺少判断能力。

用户调研中暴露的主要问题不是“业主不知道装修流程”，而是：

- 看不懂钱具体花在哪里。
- 不知道报价是否漏项。
- 不知道后期会不会增项。
- 销售承诺听起来很好，但合同里未必写清。
- 出了问题不知道找谁负责。
- 责任边界不清，后续容易出现推诿。

### 2.2 项目方向修正

项目早期曾尝试面向装修公司销售端，帮助销售生成报价和责任说明。但调研后发现，很多装修公司未必有动力主动透明化。真正更强烈、更直接的痛点在业主端。

因此产品方向调整为：从“帮助装修公司销售解释报价”转向“帮助业主审查报价、合同与销售承诺风险”。

## 3. V1 MVP 范围

### 3.1 V1 聚焦场景

V1 只聚焦“签约前风险审查”。目标是在业主签约付款前，帮助其发现报价、合同和销售承诺中的不确定点，并生成可直接使用的追问清单。

### 3.2 V1 核心能力

V1 只包含以下能力：

- 报价单审查：识别报价不清、计价方式模糊、疑似漏项、后期增项风险。
- 合同条款审查：识别付款节点、增项结算、工期、材料替换、验收和售后条款中的风险表达。
- 销售承诺核对：识别“无增项、全程管理、赠送项目、品牌材料、售后负责”等承诺是否落入合同或补充协议。
- 签约前追问清单：生成可复制给销售或装修公司的追问问题。
- 人工复核提示：标记 AI 不应直接下结论、需要人工进一步判断的事项。

### 3.3 V1 暂不包含

以下能力移动到后续迭代，不作为当前核心场景：

- 施工中问题复核。
- 交付前验收复核。
- 施工过程责任追踪。
- 多版本合同/报价对比。
- 人工顾问后台。
- 支付与商业化闭环。
- 真实账号体系。

## 4. 产品目标

### 4.1 用户目标

- 在签约前快速理解装修材料中的主要风险。
- 知道哪些报价项、合同条款和销售承诺需要追问。
- 获得一份可以复制给销售、装修公司或人工顾问的追问清单。
- 明确哪些问题需要人工复核，避免误以为 AI 可以直接判责。

### 4.2 业务目标

- 形成一个可展示 FDE 能力的 AI + RAG 业务原型。
- 体现从用户调研到产品重定位的业务判断。
- 展示如何把复杂装修风险转化为可解释、可操作的审查流程。
- 为后续接入真实文档解析、真实 embedding、向量数据库和人工复核服务打基础。

### 4.3 技术目标

- 建立“用户材料 → 知识检索 → LLM 审查 → 结构化报告 → 前端展示”的完整链路。
- 支持合同模板、消费提示、案例经验、验收标准等多来源知识库。
- 支持按城市和签约前审查阶段进行知识路由。
- 保留确定性兜底逻辑，避免 LLM 失败时产品不可用。

## 5. 目标用户

### 5.1 核心用户

准备签装修合同、已经拿到报价单或套餐方案的业主。

典型特征：

- 第一次装修或缺少装修经验。
- 面对较高金额的装修预算，担心被坑。
- 已与装修公司销售沟通，但无法判断承诺是否可靠。
- 想在签约前拿到一份“该问什么”的清单。

### 5.2 次级用户

- 第三方监理或装修顾问。
- 装修内容创作者。
- 消费者权益类咨询服务方。
- 装修平台的签约前风控模块。

## 6. V1 使用场景

### 6.1 签约前报价审查

业主拿到报价单后，输入报价内容，系统识别费用拆分是否清楚、是否存在高频漏项、是否存在“按实际发生结算”“套餐外另计”等后期增项风险。

### 6.2 签约前合同条款审查

业主输入合同草案或合同关键条款，系统识别付款节点、工期、材料替换、验收、增项、售后、违约责任等表述是否明确。

### 6.3 销售承诺核对

业主把聊天记录或销售口头承诺整理输入，系统提取“无增项、全程管理、赠送项目、材料品牌、售后责任”等承诺，并提示是否需要写入合同附件或补充协议。

### 6.4 签约前追问清单生成

系统把风险点转化为用户可直接复制给销售的问题列表，用于签约前确认、补充协议沟通或人工顾问复核。

## 7. 核心用户路径

### 7.1 主路径

1. 用户进入资料输入页。
2. 填写装修模式、城市、面积、项目名称。
3. 输入报价单文本、合同文本、销售沟通记录，或上传附件。
4. 系统校验：报价单文本、合同文本、销售沟通记录三者至少填写一项，否则不能开始审查。
5. 用户点击“开始 AI 风险审查”。
6. 进入 AI 审查过程页，查看系统解析、触发词、审查依据匹配、风险生成过程。
7. 进入风险提示总览页，查看综合风险、风险卡片和建议动作。
8. 进入结构化报告页，查看表格化结果并导出或复制报告内容。

### 7.2 异常路径

- 后端不可用：前端使用本地规则和本地知识库兜底生成报告。
- LLM 调用失败：后端使用检索命中依据和确定性规则生成兜底结果。
- 知识库未命中：提示用户补充更完整的报价、合同或沟通记录。
- 缺少输入材料：提示用户至少填写报价单文本、合同文本、销售沟通记录中的一项。
- 内容涉及法律判断：标记为人工复核，不直接给出确定性法律结论。

## 8. 功能需求

### 8.1 资料输入页

#### 功能说明

收集用户装修签约材料，明确审查范围。

#### 输入字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 装修模式 | 下拉选择 | 是 | 整装/全包/半包、散装、局改、纯服务、混合 |
| 城市 | 文本 | 否 | 用于优先匹配地方合同模板 |
| 面积 | 文本 | 否 | 用于补充项目背景 |
| 项目名称 | 文本 | 否 | 用于报告标题 |
| 报价单文本 | 多行文本 | 条件必填 | 与合同文本、销售沟通记录三者至少填写一项 |
| 合同文本 | 多行文本 | 条件必填 | 与报价单文本、销售沟通记录三者至少填写一项 |
| 销售沟通记录 | 多行文本 | 条件必填 | 与报价单文本、合同文本三者至少填写一项 |
| 附件上传 | 文件 | 否 | 当前为展示入口，后续接入真实文档解析 |

#### 输入校验

- 报价单文本、合同文本、销售沟通记录三者必须至少填写一项。
- 三者都为空时，“开始 AI 风险审查”不可继续，页面提示用户补充至少一种材料。
- 城市、面积、项目名称可以为空，但缺失时会降低报告上下文完整度。

#### 展示内容

右侧展示“本次审查范围说明”，强调系统关注：

- 费用是否说清。
- 承诺是否落纸。
- 责任是否可追。
- 漏项和增项是否提前确认。

### 8.2 AI 审查过程页

#### 功能说明

展示系统不是直接生成结论，而是经过材料解析、触发词识别、审查依据匹配和风险生成。

#### 流程步骤

1. 文档解析。
2. 触发词提取。
3. 审查依据匹配。
4. 风险生成。
5. 人工复核判断。

#### 页面内容

- 当前系统信息：LLM provider、Prompt version、生成耗时。
- 风险生成摘要。
- 本次输出重点。
- 建议下一步。
- 审查依据匹配摘要。
- 依据来源统计。
- 命中的审查依据列表。

#### 文案原则

面向 C 端用户，避免直接暴露过多技术术语。页面可以展示 RAG 和 LLM，但应转译为“审查依据匹配”“AI 风险生成”等用户可理解表达。

### 8.3 风险提示总览页

#### 功能说明

用风险仪表盘和卡片，让用户先看结论，再看原因和追问建议。

#### 顶部仪表盘

- 综合风险等级。
- 安全分 safety_score。
- 高风险数量。
- 中风险数量。
- 疑似漏项数量。
- 建议追问数量。
- 人工复核事项数量。
- 知识命中数量。

#### 分数定义

V1 统一使用 `safety_score`，表示安全分，范围 0-100，分数越高表示签约材料越清楚、风险越低。

示例：

- `safety_score = 85`：材料相对清楚，仍需确认部分问题。
- `safety_score = 55`：存在较多不确定点，建议补充书面确认。
- `safety_score = 20`：高风险较多，建议暂缓签约并人工复核。

避免使用 `risk_score = 100/100` 这类表达，以免用户误解为“风险越高越好”或“满分报告”。

#### 风险卡片字段

| 字段 | 说明 |
| --- | --- |
| 风险名称 | 例如“按实际发生结算”“以现场为准” |
| 风险等级 | 高/中/低 |
| 风险解释 | 为什么该项可能产生后续争议 |
| 建议追问 | 用户可以直接问销售的问题 |
| evidenceId | 至少绑定 1 条审查依据 ID |
| 命中依据 | 来自合同库、消费提示、案例库或经验库 |
| 人工复核 | 是否建议人工进一步判断 |

### 8.4 结构化报告页

#### 功能说明

将风险审查结果转为可归档、可导出、可复核的结构化内容。

#### Tab 内容

1. 风险明细表。
2. 疑似漏项表。
3. 责任边界待确认表。
4. 签约前追问清单。
5. 人工复核任务。
6. 结构化 JSON。

#### 导出与复用能力

V1 保留 CSV 导出作为结构化数据导出，同时规划以下输出能力：

- 复制追问清单：一键复制可发送给销售或装修公司的问题列表。
- 导出 Markdown 风险报告：用于保存、转发、二次编辑。
- 导出 PDF 风险报告：用于归档或人工顾问复核。
- 生成可发送给销售的问题列表：把风险卡片转化为更自然的沟通话术，但不生成诱导性销售话术。

## 9. RAG 知识库需求

### 9.1 主库

当前主库文件：

`knowledge/owner-risk-rag-master.json`

当前共 165 条知识卡。

### 9.2 来源构成

| 来源文件 | 数量 | 作用 |
| --- | ---: | --- |
| `owner-risk-rag.json` | 37 | 旧基准库，包含合同风险、报价风险、消费提示和基础经验 |
| `owner-risk-rag-supplement.json` | 120 | 验收/材料标准 20 条 + 案例库 100 条 |
| `contract-template-cards.json` | 8 | 合同模板知识卡，包含京津冀与全国模板 |

### 9.3 可信分层

| 层级 | 类型 | 用途 |
| --- | --- | --- |
| A | 合同硬知识、合同模板、验收/材料标准 | 作为最强审查依据 |
| B | 市场监管、消协等消费提示 | 作为公共风险提示依据 |
| C | 典型案例库 | 用于识别常见争议场景 |
| D | 用户经验与基础规则 | 用于补充经验风险，但不作为强结论依据 |

### 9.4 地区合同模板路由

用户输入城市后，系统优先匹配地方或区域合同模板；如果没有地方模板，则使用全国模板。

路由原则：

1. 城市命中地方模板：优先使用地方模板。
2. 城市命中区域模板：使用区域模板 + 全国模板。
3. 未命中地方模板：使用全国模板。
4. 所有模板知识仍需结合用户材料，不直接做法律结论。

### 9.5 当前检索方式

当前 V1 原型采用“结构化知识卡 + 关键词/规则评分/本地相似度检索”的方式召回审查依据。

当前尚未接入真实 embedding 模型和向量数据库。因此，文档中不应表述为已经完成标准语义向量检索。后续可升级为真实 embedding + 向量数据库的标准 RAG 架构。

## 10. LLM 与知识检索工作机制

### 10.1 整体链路

```text
用户输入材料
↓
后端结构化接收
↓
城市 / 签约前审查阶段 / 装修模式路由
↓
知识检索器召回审查依据
↓
LLM 风险审查 Agent
↓
结构化 JSON 风险报告
↓
前端四页展示
```

### 10.2 知识检索的作用

知识检索不直接负责“下结论”，它负责：

- 根据城市和签约前审查阶段限定知识范围。
- 从合同模板、消费提示、案例经验、验收标准中检索相关依据。
- 将命中的依据作为上下文提供给 LLM。
- 在 LLM 不可用时提供确定性兜底判断依据。

### 10.3 LLM 的作用

LLM 负责：

- 结合用户输入和命中依据进行风险解释。
- 把风险点组织成用户能理解的语言。
- 生成追问清单、人工复核事项和结构化 JSON。

### 10.4 当前模型状态

当前项目已经接入 LLM 调用链路，并通过 OpenAI-compatible 接口调用硅基流动模型。

当前尚未接入真实 embedding 模型和向量数据库。当前检索更准确地说是“结构化知识卡 + 关键词/规则评分/本地相似度检索”的混合检索原型。

## 11. Prompt 需求

### 11.1 Agent 角色

业主装修报价与承诺风险审查助手。

### 11.2 Prompt 目标

基于用户输入的报价单、合同文本、销售沟通记录，以及系统检索到的审查依据，生成签约前风险审查结果。

### 11.3 约束

- 只能基于用户材料和检索依据判断。
- 不编造法律结论。
- 每个风险卡片必须绑定至少 1 条 `evidenceId`。
- 没有依据的内容只能进入人工复核，不生成确定性结论。
- 不输出“违法”“必然败诉”等确定性法律判断。
- 输出必须为可解析 JSON。
- 报告中必须展示边界说明：本产品不替代律师、监理或司法判断。

## 12. 非功能需求

### 12.1 可用性

- 页面路径清晰：资料输入 → AI 审查 → 风险总览 → 结构化报告。
- 结论优先，表格后置。
- 技术过程可解释，但不过度后台化。

### 12.2 可信感

- 展示依据来源。
- 展示人工复核边界。
- 明确报告不构成法律意见。
- 高风险用红色克制提示，不做恐吓式表达。

### 12.3 性能

- 本地运行时页面响应应保持流畅。
- 后端 LLM 请求失败时必须有兜底结果。
- 知识库检索应在秒级完成。

### 12.4 隐私与安全边界

用户上传或输入的材料可能包含姓名、电话、地址、合同编号、房屋地址、付款信息、聊天记录等敏感信息。

V1 原型必须遵守以下边界：

- 调用外部 LLM 前，应提示用户对姓名、电话、地址、合同编号等敏感信息进行脱敏。
- 调用外部 LLM 前，应获得用户授权，并说明材料可能被发送到外部 API。
- 未经授权，不应把用户材料发送到第三方服务。
- 当前为本地原型，不处理真实账号体系、商业支付和长期云端存储。
- 后续上线版本需要补充隐私政策、数据保留周期、删除机制和日志审计。

## 15. 成功指标

### 15.1 作品集展示指标

- 观众能在 3 分钟内理解产品解决的是“签约前看不懂、怕漏项、怕承诺不落纸”的问题。
- 能清楚展示从用户调研到产品从 B 端转向 C 端的判断过程。
- 能说明知识检索与 LLM 的分工：先找依据，再生成风险解释和追问清单。
- 页面呈现像 C 端专业审查工具，而不是后台数据看板或静态 Demo。
- 能展示至少 3 类输出：风险卡片、追问清单、结构化报告。

### 15.2 产品验证指标

- 用户是否愿意在签约前输入或上传报价单、合同条款、销售沟通记录。
- 用户是否认为追问清单可直接发送给销售或装修公司。
- 用户是否能理解“AI 不判案，只提示风险”的边界。
- 用户是否愿意根据报告补充询问或暂缓签约。
- 用户是否愿意为人工复核、监理咨询或深度报告付费。

## 17. 项目展示口径

本项目是一个面向业主的装修签约前 AI 风险审查原型。它不是替用户打官司，也不是替装修公司生成销售话术，而是把业主看不懂的报价单、合同条款和销售承诺，转化为可解释、可追问、可复核的风险报告。

项目核心体现三点能力：

1. 业务理解：从装修公司 B 端销售工具，调整为更符合真实痛点的 C 端风险审查工具。
2. AI 架构：先通过结构化知识卡和本地检索召回可信依据，再由 LLM 生成结构化风险报告。
3. 产品表达：把复杂风险拆成用户能看懂的结论、卡片、追问清单和结构化表格。
